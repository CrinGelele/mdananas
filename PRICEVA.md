# Запуск сайта и импорта Priceva

Рекомендуется Python 3.11 и установленный ODBC Driver 17 for SQL Server.
Подключения `ideal` (IDEAL) и `default` (MDANANAS) остаются в настройках проекта.

Из корня репозитория обновить зависимости:

```powershell
py -m pip install -r requirements.txt
cd mdananas
```

Обычный запуск одной командой:

```powershell
py manage.py runsite
```

Команда запускает `runserver` и отдельный `pricem_worker`, используя тот же Python.
Перезагрузка кода сайта не перезапускает импортёр. Изменения кода самого импортёра
подхватываются после остановки и нового запуска `runsite`. `Ctrl+C` останавливает
оба процесса. При завершении одного из процессов команда останавливает второй и
возвращает ошибку. После выключения компьютера команду нужно запустить снова.

Другой адрес и отключение перезагрузки кода:

```powershell
py manage.py runsite 0.0.0.0:8000 --noreload
```

## Первое обновление БД

Перед первой проверкой подготовить схему на компьютере с доступом к БД.
Сначала сохранить резервную копию БД и проверить SQL-отчёты, использующие `upload_time`:
его тип меняется с целого часа на `time(0)` с минутами. Логика таких отчётов может
потребовать изменения. Старое поле сохраняется как `upload_time_legacy_hour`.
Для старых записей известен только час: `9` преобразуется в `09:00:00`.
Минуты исторических загрузок восстановить из прежнего поля нельзя.

Подготовка и запуск одной командой:

```powershell
py manage.py runsite --prepare-pricem
```

Флаг выполняет `datapull_service/sql/001_pricem_import.sql` на соединении `ideal`.
Скрипт транзакционный и допускает повторное выполнение. Он добавляет:

- точное плановое время в `PRICEM_DATA_Source_Offers.upload_time`;
- идентификаторы Priceva в товарах и источниках с уникальными фильтрованными индексами;
- таблицу `MDANANAS.dbo.DATAPULL_PRICEM_RUNS` для состояний, снимков JSON и диагностики.

При некорректных исторических часах или обнаруженных зависимостях SQL от старого
поля скрипт остановится и откатится. Динамические SQL-зависимости не всегда видны
в системном каталоге, поэтому проверка внешних отчётов нужна отдельно.
Таблица состояний и бизнес-таблицы должны находиться на одном SQL Server:
запись данных и отметка успеха используют одно соединение и одну транзакцию.

Подготовить только БД, без запуска сайта:

```powershell
py manage.py pricem_prepare
```

## Правила расписания

Расписание ежедневно повторяется по московскому времени. `pricem_worker` перечитывает
таблицу каждые 15 секунд, поэтому изменения из интерфейса не требуют его перезапуска.
Для каждой записи формируется конкретный пункт с датой и временем.

Импорт начинается в минуту пункта расписания. Пропущенный последний пункт догружается,
если до следующего пункта осталось не меньше 30 минут. Ровно 30 минут допускаются.
Дубли времени и значения вне диапазонов 0..23 / 0..59 считаются ошибкой расписания.
Для интервала короче 30 минут доступен обычный запуск в минуту пункта, но догоняющего
окна нет. Единственный пункт повторяется на следующий день.

Все пункты должны соответствовать действительным заменам выгрузки в Priceva.
Отключённая запись запрещает её импорт, но продолжает ограничивать окно предыдущего
пункта, поскольку данные в Priceva всё равно заменяются. Для времени после полуночи
предыдущий пункт может относиться к вчерашнему дню.

`upload_date` и `upload_time` берутся из планового пункта по Москве.
Например, запуск в 11:10 за пункт 09:30 сохраняет `09:30:00`, а не `11:10:00`.
Служебные DateTime-поля в таблице запусков сохраняются в UTC.

## Ошибки, повторы и снимки

Перед записью цен полный ответ API сохраняется в таблице запусков вместе с SHA-256.
JSON проверяется целиком. Изменения товаров, источников, цен и запись об успехе
выполняются в одной транзакции. Неуспешная попытка откатывается.
При повторе используются сохранённые данные, даже после следующей замены в Priceva.
Снимки хранятся в БД; их резервное копирование и размер входят в обслуживание этой БД.

SQL-блокировка `sp_getapplock` защищает от нескольких импортёров, в том числе на разных
компьютерах. Разрыв соединения или завершение процесса освобождает блокировку.
Незавершённый запуск с сохранённым снимком восстанавливается следующим процессом.
Успешный пункт повторно не импортируется.

Временные сетевые ошибки, HTTP 429/5xx и `OperationalError` повторяются с паузами
1, 5 и 15 минут, максимум четыре автоматические попытки. Новую выгрузку нельзя
скачивать за пределами доступного окна. Ошибки данных, неоднозначные старые
сопоставления товаров и исчерпанные попытки требуют исправления причины и явного повтора.

Одиночное предложение без `offer` получает пустую строку; отсутствующий
`last_check_date` сохраняется как NULL. Неверные типы и слишком длинные поля
дают ошибку с номером товара/источника, без вывода всего содержимого записи.
Ручные сопоставления с TU/MIX/CMP сохраняются. Новые предложения заменяют только
снимок с той же плановой датой и временем; другие пункты не затрагиваются.

Старые `LOGS_DATAPULL_PRICEM` не подтверждают полноту прежних загрузок и не используются
для автоматического объявления пункта успешным. Неполные исторические загрузки с
неверной датой/часом нужно сверять отдельно. Дубли товаров проверяются до начала
записи данных. Если у дублей один тип (INT/EXT) и полностью одинаковые ручные
привязки, импортёр создаёт новую строку с ID Priceva и общей привязкой. Старые
строки сохраняются. Число таких новых товаров записывается в `counts` как
`products_created_for_legacy_duplicates`.

Если привязки различаются, текущий `article` из снимка сравнивается с EAN у CMP
или xcode у TU/MIX. При ровно одном совпадении используется соответствующая
существующая строка, сохраняя её ручную привязку и историю остальных строк.
`client_code` может сохраняться при смене SKU, поэтому он не заменяет `article`
при такой проверке. Существующее сопоставление по точному ID Priceva всегда
имеет приоритет и не меняется из-за нового артикула.

Оставшиеся конфликты требуют ручного выбора. Импорт сообщает общее число
конфликтов, код товара, тип/ID строки и её привязку (до 10 товаров за сообщение).
Для явного выбора существующей строки предусмотрена отдельная команда:

```powershell
py manage.py pricem_bind_product --run 123 --client-code YOUR_CODE --kind ext --product-id 456 --check
py manage.py pricem_bind_product --run 123 --client-code YOUR_CODE --kind ext --product-id 456
py manage.py pricem_run --retry-run 123
```

Сначала выбрать правильную строку и сверить результат `--check`. Команда берёт
ID Priceva из проверенного сохранённого снимка и меняет только
`priceva_product_id` выбранной строки. Ручные привязки и остальные строки
сохраняются. Запись защищена общей блокировкой и транзакцией. Чужой ID Priceva
не заменяется; привязка ID, уже занятого другой строкой, запрещена. Состояние
запуска остаётся прежним до отдельного повтора `pricem_run`.

Если одному источнику Priceva соответствуют несколько старых источников без ID
Priceva с одинаковыми товаром, URL, покупателем, регионом и вариантом продажи,
импортёр создаёт отдельную строку с точным ID Priceva. Старые источники и их связи
сохраняются; цены других пунктов расписания и дополнительные данные старых
источников остаются на прежних ID. Дальнейшие импорты используют новую строку по
ID Priceva. Число созданных таким образом источников записывается в `counts` как
`sources_created_for_legacy_duplicates`. Единственный подходящий старый источник
по-прежнему получает ID Priceva без создания новой строки.

## Проверки на компьютере с БД

Узнать текущий пункт и доступность окна без API-запросов и записей:

```powershell
py manage.py pricem_run --check
```

Выполнить одну проверку расписания и доступный импорт, без ожидания следующего пункта:

```powershell
py manage.py pricem_run
```

Повторить исправленный запуск по его ID, используя сохранённый снимок:

```powershell
py manage.py pricem_run --retry-run 123
```

Без сохранённого снимка явный повтор тоже соблюдает окно доступа к данным.
Второй `pricem_run` после успеха не должен делать API-запрос и менять количество цен.
Если работает `runsite`, одноразовая команда может вывести `busy`: импорт уже выполняется.

Диагностика в SQL Server без вывода самого JSON:

```sql
SELECT TOP (20)
    id, schedule_id, DATEADD(hour, 3, scheduled_at) AS scheduled_at_msk,
    status, attempts, started_at, finished_at, next_retry_at,
    fetched_at, LEN(payload) AS snapshot_chars, counts, last_error
FROM [MDANANAS].[dbo].[DATAPULL_PRICEM_RUNS]
ORDER BY id DESC;

SELECT upload_date, upload_time, COUNT_BIG(*) AS offers_count
FROM [IDEAL].[03_PRICEM].[PRICEM_DATA_Source_Offers]
GROUP BY upload_date, upload_time
ORDER BY upload_date DESC, upload_time DESC;
```

Первый интеграционный прогон: подготовка схемы, `--check`, один доступный импорт,
проверка статуса `succeeded` и счётчиков, повтор без изменения цен, затем `runsite`.
Откат посреди записи и восстановление после аварии проверять в копии БД.

## Локальные тесты без SQL Server

Из корня репозитория, в отдельном окружении с Django и requests:

```powershell
py -m unittest discover -s tests -v
```

Тесты используют только SQLite в памяти, изолированные настройки и заглушку API.
Они проверяют расписание, полный JSON-пример из репозитория, реальные ORM-записи
и откат транзакции, восстановление, сохранение ручных связей и остановку процессов.
SQL Server DDL, ODBC и фактическое поведение Windows проверяются отдельно на втором ноутбуке.
